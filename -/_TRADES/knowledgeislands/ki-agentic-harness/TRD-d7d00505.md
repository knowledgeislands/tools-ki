# TRD-d7d00505: Let rubric items yield while their subprocesses run

## Context

The `ki` host reports rubric item progress at both edges of each item and refreshes its live display on a timer between those edges, so that the elapsed clock and the indeterminate sweep advance while a single long item runs. That refresh is inert whenever the running item blocks the event loop, because a timer callback cannot be delivered while the loop is blocked, and the display then sits frozen on the item that is still running. A user cannot distinguish that from a hang, which is precisely the state the refresh exists to rule out.

## Submission

Consider having rubric items that shell out use asynchronous subprocess execution rather than a synchronous call, so that a running item yields the event loop between starting its subprocess and collecting its result. The host needs nothing else: it already awaits each item, so a yielding item is sufficient for the refresh to be delivered, the elapsed clock to advance, and the running item's name to remain visibly current. The measurement below is from `ki repo audit --skill ki-engineering` against the tools-ki repository, and re-running it after any change would confirm the effect directly: the refresh timer registered once and fired zero times across 26.5 seconds of wall clock, where roughly one hundred and six firings were due at the configured interval, and the corresponding frame capture held eighty-eight frames carrying only three distinct clock values, jumping from `0.0s` to `30.5s` with no refresh frame among them. The tools-ki record for the concurrent-coverage race, since reverted for unrelated reasons, independently noted that the `ki-engineering` audit evidence context runs its checks synchronously, which is the same mechanism seen from a different direction.

## Constraints

The Harness owns the rubric contract, the evidence-context helpers, and whether this is worth changing at all; this is an observation with a measurement attached, not an agreed design. Serialisation matters and is not being asked to change: items within a skill share a stateful session and must continue to run one at a time, so the request is that an item yield while it waits, not that items overlap. The host will not reclaim the event loop on its own behalf. Running items in a worker thread or child process would make the display independent of item behaviour, but it would alter the execution model of every rubric to solve a presentation problem and introduce serialisation and failure semantics at a boundary that has none today, so tools-ki considers that disproportionate and has recorded it as rejected rather than deferred. If the Harness declines or defers, tools-ki will consider saying something explicit when an item has run without yielding, so that a frozen clock is at least attributable.
