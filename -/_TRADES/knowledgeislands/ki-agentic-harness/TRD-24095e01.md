# TRD-24095e01: Improve Guides feature routing

## Context

Reclassifying `tools-ki` developer documentation under `docs/guides/` made the current four-document split concrete: Decisions explain why, Feature Definitions describe as-built observable behaviour, guides explain how, and roadmap items describe planned work. The Guides standard states this boundary, but its EDUCATE and CONFORM guidance does not yet prompt a repository to inspect or establish Feature Definitions when a guide depends on stable system behaviour.

## Submission

Consider strengthening `ki-guides`' practical routing: when establishing or reviewing a guide collection, direct authors to the repository's Feature Definitions corpus for behaviour that a guide relies on, and to `ki-feature-definitions` when that corpus is absent or incomplete. Preserve the existing distinction: the guide links to behaviour but does not restate its normative contract.

## Constraints

This is a knowledge submission, not an instruction to change the portable standard. The Harness retains all decisions on whether the finding warrants a skill, rubric, or exemplar change. Do not require every repository to create Feature Definitions merely because it has a guide; route based on whether the guide needs a stable as-built behaviour contract. Keep `ki-guides` and `ki-feature-definitions` independently usable and avoid creating duplicate requirements.
